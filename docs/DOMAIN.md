# 配额领域模型与推荐规则

本文定义领域约束与验收标准，v0.1.0 的领域规则已实现在 Rust 中，实际交付范围见 [当前实现](IMPLEMENTATION.md)。上游字段的真实含义由适配器核实后映射；领域层不猜测 Cockpit 的文件结构、套餐限制或服务端行为。

## 1. 领域边界

官方客户端或 Cockpit 负责账号登录。HUD 只读账号来源、查询配额、展示状态并推荐当前可使用的账号，不登录、不刷新 OAuth token、不写回来源文件、不切换账号。

Rust 领域层计算配额状态与推荐结果，前端和主题只负责展示。更换主题不能改变可用性、排序、刷新频率或请求目标。

推荐仅表示“根据最近一次可靠查询得到的判断”。它不保证下一次请求一定成功，也不预测其他客户端随后消耗的额度。

## 2. 账号和窗口模型

### 2.1 账号标识

- 对公开接口使用稳定、不含邮箱或 token 的 HUD 不透明账号 ID。
- 用户可见名称、邮箱前缀和用户自定义别名仅用于展示，允许重名。
- 账号选择和排序使用 ID；不能用展示名称作为主键。
- 仅选中的账号参与推荐。账号被删除、取消选择或切换来源后，晚到请求结果不能使它重新参与推荐。
- 未选中的账号不查询配额；读取账号列表和执行配额查询是不同操作。

### 2.2 配额窗口

每个窗口使用以下归一化语义。字段命名以公开 API 契约为准，本文约束其含义。

| 字段 | 含义 |
| --- | --- |
| `id` | 账号内稳定窗口 ID。主窗口可使用 `primary` / `secondary`；附加窗口使用不冲突的 ID，不能全部命名为同一个 `additional`。 |
| `scope` | `base` 表示基础配额；`feature:<name>` 表示独立功能配额。 |
| `kind` | `primary`、`secondary`、`other`，表达上游窗口角色，不等同于固定时长。 |
| `durationSeconds` | 上游可确认的窗口时长；无法确认时为 `null`，不能凭角色填入 5 小时或 7 天。 |
| `applicability` | `required`、`not_applicable`、`unknown`，分别表示适用、不适用、尚不能确认。 |
| `measurement` | `percent`、`unlimited`、`unknown`。无限额度必须有明确证据。 |
| `remainingPercent` | 未经显示四舍五入的剩余百分比，范围为 0–100；不适用、无限或未知时为 `null`。 |
| `exhausted` | `true`、`false` 或 `null`。`null` 表示无法判断是否耗尽，不等同于 `false`。 |
| `resetsAt` | 已核实的 UTC RFC 3339 重置时间；不存在或未知时为 `null`。 |

补充约束：

- `measurement=percent` 时必须有有效的 `remainingPercent`，且适配器必须提供可靠的 `exhausted`。不能让领域层通过格式化后的百分比推导耗尽状态。
- 如果上游只提供已用比例，由已核实语义的适配器执行转换，再交给领域层；不能假设所有 Provider 的原始值都采用同一单位。
- 明确无限的规范表示为 `measurement=unlimited`、`remainingPercent=null`、`exhausted=false`，通常没有重置时间。不能把缺字段转成无限额度。
- 无效数值、无法解析的时间和互相矛盾的字段必须产生可诊断的未知状态；不能静默填入 0、100 或当前时间。
- `not_applicable` 的窗口不构成限制。`unknown` 的基础窗口必须阻止正向推荐。
- `feature:<name>` 即使 `applicability=required`，也只对该功能适用。V1 基础推荐仅使用 `scope=base`，不能把附加功能耗尽误判为整个账号不可用。
- 适配器需要为无法判定的预期基础限制保留未知状态；不能通过遗漏字段让一个不完整账号看起来可用。空窗口列表不代表无限额度。
- “5h / 7d”是已知时长的展示标签。解析器、领域结构和排序不能假设 `primary` 永远为 18,000 秒、`secondary` 永远为 604,800 秒。

### 2.3 周限额单独存在与折叠估算

配额响应中一个基础槽位包含有效 604,800 秒百分比窗口、另一个槽位为 null 或不存在时，适配器将不存在的槽位标为 `not_applicable`。周窗口可以在 primary 或 secondary 中；存在但格式损坏的另一槽位仍为未知，不得按“只有周限额”放行。推荐阈值按真实时长应用：5H ≥ 5%，周 ≥ 2%；没有 5H 限制时只检查周额度。

快照的 `totalQuota` 为 `{percent: number|null, partial: boolean, weeklyScalePercent: 15}`，由 Rust 在与推荐相同的采样时刻计算，只统计已选且可信的基础配额。双限额账号贡献 `H × min(W/15, 1)`，单周限额账号贡献 W。H 和 W 均是未经显示取整的剩余百分比。小于推荐阈值的正余额仍可贡献总量；推荐阈值不改变估算公式。重复 ID 不重复计入，总量允许超过 100%。

15% 是本项目使用的估算规则，[OpenAI 官方说明](https://learn.chatgpt.com/docs/pricing) 未提供固定的 5H/周额度换算比例。不同账号套餐的百分比汇总也不表示实际可执行的统一 token 数量。

缓存、过期、失败、已越过重置边界或约束不明确的账号不贡献估算值。有部分可信数据时 `partial=true`，圆球显示已知总量，不加约等号，部分状态保留在无障碍说明与接口中；全部未知时 percent=null，显示 `—`，不能伪造 0%。可信且完整的总量恰为 0 时，圆球显示推荐的最近可用倒计时；倒计时到期仍需服务端核实。

### 2.4 账号配额快照

| 字段 | 含义 |
| --- | --- |
| `origin` | `network`、`cockpit_cache` 或 `none`。标明当前展示数据的来源；尚无任何样本时使用 `none`。 |
| `freshness` | `fresh`、`stale` 或 `unknown`。反映当前数据是否仍在可信时间范围内。 |
| `lastSuccessAt` | 最近一次成功完成直接网络查询的 UTC 时间。没有成功记录时为 `null`。 |
| `lastAttemptAt` | 最近一次直接查询尝试的 UTC 时间，包括失败尝试。 |
| `status` | `ok`、`refreshing`、`auth_expired`、`unavailable` 或 `error`。 |
| `providerAllowed` | 归一化后的基础使用许可：`true`、`false` 或 `null`。`null` 表示当前无法可靠判断。 |
| `baseCoverageComplete` | 适配器是否已经核实基础限制覆盖完整，不能仅按数组非空推断。 |
| `blockingReason` | `none`、`quota_windows`、`other`、`unknown`，说明许可/阻断是否可由已知基础窗口解释。 |
| `error` | 最近一次已完成查询的失败信息；开始重试不清除此字段，成功后才清除。 |
| `windows` | 上述窗口列表。 |

以上时间和状态按账号维护，不能用某一个账号的成功刷新时间替其他账号更新有效期。

首次查询前 `origin=none`、`freshness=unknown`、`lastSuccessAt=null`，不得用默认的 network/ok 表示尚不存在的成功结果。`observedAt` 表示展示样本的时间，`validUntil` 只表示年龄截止时间，重置边界或错误仍可能更早使数据失效。

`providerAllowed` 必须表达基础使用状态。若上游只有特定功能的允许标记，应映射到对应功能语义，不能冒充全账号基础许可。

`status=refreshing` 只说明正在请求。已有快照如果仍满足全部可信条件且 `error=null`，可以继续显示原推荐及其采样时间；刷新开始不能延长有效期。没有可靠历史快照或上次失败尚未被成功覆盖时仍为 `unknown`。

失败保留旧快照仅用于灰色历史展示。即使 `lastSuccessAt` 还很近，`auth_expired`、`unavailable`、`error` 都必须排除该账号的推荐资格；不能把失败请求更新为成功时间。

本地缓存的读取时间不能当作服务端采样时间。`origin=cockpit_cache` 在 V1 仅供历史展示，不参与 `now` 或确定等待时间的推荐。

## 3. 时间、新鲜度和重置确认

### 3.1 新鲜度

自动刷新间隔默认 5 分钟，可配置范围为 1–30 分钟。网络快照的有效时长为：

```text
freshnessLimitSeconds = max(2 × refreshIntervalSeconds, 120)
```

默认有效时长为 10 分钟。达到该时长即为 `stale`，不是再等待下一次定时任务运行后才过期。改变刷新间隔后立即重算有效性。

只有直接成功网络查询、成功时间有效且未超龄的数据，才可能是 `fresh`。缺少时间、无法解析时间或系统时钟异常导致不能可靠计算年龄时，使用 `unknown`，不能以负的年龄延长有效期。

实现应使用单调时钟维护同一运行周期内的经过时长，使用 UTC 时间表达服务端重置时刻。系统唤醒或检测到时钟明显变化后重新校验并请求刷新。

### 3.2 重置到点不是刷新成功

如果任一适用的基础窗口包含 `resetsAt <= now`，其旧采样已经跨越重置边界。无论年龄是否仍在有效期内，该账号都进入派生状态 `unknown`，原因是 `awaiting_confirmation`，触发一次合并刷新。

`awaiting_confirmation` 是领域计算原因，不新增到上表的 `status` 枚举中。界面可显示“等待更新”；不能把倒计时归零自动转换为 `now`，也不能自动把剩余比例改成 100%。

已知窗口没有重置时间，不会凭空产生重置边界。若其当前额度可靠且未耗尽，仍可判断当前可用；若已经耗尽，则无法计算恢复时间。

刷新响应仍携带已过去的重置时间时，继续等待确认并进入受控退避，不能形成每帧或每秒重复刷新的循环。

### 3.3 时间展示

- 时间统一存储为 UTC，在用户本地时区展示，倒计时由时间差计算。
- 倒计时最小显示为 0，不显示负数；跨越重置时刻立即重新计算领域状态。
- 剩余比例在 0 与 1 之间时，紧凑视图显示 `<1%`，避免真实仍有余额却显示成 `0%`。
- `0%`、未知和无限分别展示，不能混用破折号表达全部情况。
- 窗口长度未知时显示“主窗口”等语义名称，不能伪装成 5h 或 7d。

## 4. 单账号可用性

单账号计算结果为 `now`、`waiting` 或 `unknown`，并携带原因。`unknown` 可以同时表达“已知当前受限，但不知道何时恢复”；因此结果还应保留可解释的限制原因，不能仅显示一个无说明的问号。

### 4.1 计算顺序

1. 检查账号仍被选中且来源有效。
2. 检查数据来源必须为 `network`，新鲜度必须为 `fresh`，`error=null`，状态必须为 `ok` 或持有可靠历史快照的 `refreshing`。
3. 检查适用基础窗口是否跨越重置边界；跨越则返回 `unknown / awaiting_confirmation`。
4. 取基础窗口集合。忽略明确 `not_applicable` 的窗口；任何基础适用性未知、必要字段未知或配额覆盖不完整都返回 `unknown`。
5. 检查 `providerAllowed`。未知许可不支持正向推荐或确定恢复时间。
6. 根据适用基础窗口耗尽情况，得到 `now`、`waiting` 或无法确定恢复的 `unknown`。

### 4.2 当前可用

满足以下全部条件才返回 `now`：

```text
来源为直接成功网络查询，且快照仍可信
AND providerAllowed = true
AND baseCoverageComplete = true AND blockingReason = none
AND 每个适用的基础窗口均已确认 exhausted = false
AND 没有跨越尚未确认的重置边界
```

明确无限的基础窗口满足“未耗尽”，但不豁免其他限制或 `providerAllowed` 检查。

如果基础窗口全部显示未耗尽，但 `providerAllowed=false`，返回 `unknown`，说明为“服务端报告其他限制，恢复时间未知”。不能因为百分比尚有剩余就显示 `now`。

### 4.3 已知等待时间

定义 `B` 为所有 `scope=base`、`applicability=required`、`exhausted=true` 的窗口。

可以返回 `waiting` 的条件是：

- 前面的快照可信性、完整性和重置边界检查通过。
- `B` 非空，所有适用基础窗口的状态均已知。
- 每个阻断窗口都有严格晚于当前时间的已知重置时间。
- `providerAllowed` 已知，`baseCoverageComplete=true` 且 `blockingReason=quota_windows`，即上游归一化结果没有另一个无法解释或无法定时的基础阻断原因。

单账号预计恢复时刻为：

```text
estimatedAvailableAt = max(window.resetsAt for window in B)
```

只有主窗口耗尽时取主窗口重置时间；只有次窗口耗尽时取次窗口重置时间；两者都耗尽时取更晚者。此规则同样适用于其他已核实的基础限制。

这是根据已知限制计算的预计时刻，不是服务端恢复保证。`providerAllowed=false` 可以与已耗尽窗口一致；如果 Provider 不能确认该阻断可由已知窗口解释，必须返回恢复时间未知，不能猜测关联。

以下情况不能给出确定等待时间：

- 已知一个窗口耗尽且重置时间明确，但另一个适用基础窗口状态未知。
- 任一耗尽基础窗口缺少重置时间。
- 存在独立的、无法定时的服务端限制。
- `providerAllowed=null`，无法排除其他基础限制。

这些账号可以展示已知窗口信息和“已受限”，但不参与最早恢复排序。

## 5. 多账号推荐

规则适用于任意数量的已选账号，不限于两个。

### 5.1 存在当前可用账号

仅在单账号结果为 `now` 的集合中选择，输出：

```text
time to usable: <name> · now
```

排序顺序为：

1. 优先考虑存在已知未来周窗口重置时间的账号。周窗口必须同时满足 `scope=base`、`applicability=required`、`kind=secondary`、`durationSeconds=604800`。
2. 在这些账号中，`resetsAt` 更早者优先。
3. 没有适用周窗口、周窗口时长未知或周重置时间未知的账号排在已知周重置时间之后；它们仍然可能是当前可用账号。
4. 时间相同或同属未知周重置组时，按用户设置的账号顺序排序；再按稳定账号 ID 排序，避免界面抖动。

不依据最后刷新时间、账号名称或已用百分比打破平局。不把 `secondary` 的其他时长当作 7d。

### 5.2 没有当前可用账号

从单账号结果为 `waiting` 的集合中选择最小 `estimatedAvailableAt`。相同时使用用户顺序、稳定 ID 作为确定性次序。

```text
time to usable: <name> · <countdown>
```

若存在未知账号，该结果只能表示“已知账号中预计最早恢复”，必须附带覆盖不完整提示；不能宣称它一定是所有账号中最早恢复的账号。

如果没有 `now` 或 `waiting` 候选，返回 `unknown` 并说明主要原因。未选择账号时使用独立的空状态“请选择显示账号”，不伪装成接口错误。

### 5.3 覆盖情况

推荐结果应附带已选账号数量、可判断数量、未知账号数量以及异常原因摘要。

只要存在未知账号，覆盖即不完整。仍可推荐一个已知 `now` 的账号，但界面不能暗示已经成功检查全部账号。

请求失败、认证失效和本地缓存账号不会阻止其他可靠账号被推荐；它们会影响覆盖提示。

## 6. 刷新与领域状态的衔接

- 手动、定时、启动、唤醒和重置到期共用同一刷新服务，领域层只接受归一化后的结果。
- 每账号最多一个请求在途；重复刷新合并。手动刷新不绕过服务端限流和 `Retry-After`。
- 正在刷新时保留最后成功时间。成功才替换快照、重算推荐；失败按新错误状态排除推荐资格。
- 账号取消选择、数据源变更或请求被新一代配置取代后，旧响应丢弃，不能覆盖新状态。
- 获取快照和监听事件需要有一致的版本或序号，前端丢弃旧事件，不自行合并出与后端不同的推荐状态。
- 睡眠期间不积累补刷任务。唤醒后合并为一次必要刷新，先重新计算新鲜度和重置边界。
- 401 可导致 `auth_expired`。若重新读取后确认 access token 已变化，可受控重试一次；HUD 不执行 OAuth 刷新。不能把所有 403、网络错误或解析失败都展示成认证过期。
- 倒计时的每秒更新是显示计算，不是网络查询。

## 7. 后续实现验收用例

以下是必须覆盖的行为标准，当前不引入测试代码。测试使用虚构账号和脱敏固定响应，不访问真实凭据。

除特别说明外，账号已选中；快照为新鲜直接网络结果、`status=ok`；所有适用基础窗口均已完整解析，`providerAllowed` 与窗口状态一致，且没有其他未知限制。设固定当前时刻为 `T`。

| 场景 | 预期结果 |
| --- | --- |
| 单账号主、次基础窗口均有余额，许可为真 | `now`。 |
| 主窗口耗尽，重置为 `T+1h`；次窗口未耗尽 | `waiting`，预计 `T+1h`。 |
| 主窗口未耗尽；次窗口耗尽，重置为 `T+2d` | `waiting`，预计 `T+2d`。 |
| 主窗口在 `T+1h` 重置，次窗口在 `T+2d` 重置，均耗尽 | 预计 `T+2d`，不能取较早者。 |
| 三个基础阻断窗口分别在 `T+1h`、`T+2h`、`T+3h` 重置 | 预计 `T+3h`。 |
| 主窗口耗尽且时间已知，次基础窗口状态未知 | `unknown`，不得展示确定恢复时间。 |
| 一个阻断窗口没有重置时间 | `unknown`，可说明已受限。 |
| 适用基础窗口为 `measurement=unknown` | `unknown`，不得填 100%。 |
| 次基础窗口明确 `not_applicable`，主窗口可靠且有余额 | 可为 `now`；不能因为缺少 7d 而误判，也不能伪造 7d。 |
| 次基础窗口 `applicability=unknown` | `unknown`。 |
| 基础窗口明确无限，许可为真且其他基础限制已排除 | `now`，展示无限而非未知或 100%。 |
| 窗口列表为空，许可为真 | 仍为 `unknown`，不能利用空集合判定可用。 |
| 基础配额可用，某 `feature:<name>` 窗口耗尽 | 基础推荐仍可为 `now`，功能限制独立显示。 |
| 各窗口均未耗尽，但 `providerAllowed=false` | `unknown`，解释其他限制和未知恢复时间。 |
| 各窗口均未耗尽，但 `providerAllowed=null` | `unknown`，不得给正向推荐。 |
| `remainingPercent=0.4` 且明确未耗尽 | 展示 `<1%`；5H/周限额低于推荐阈值时等待重置，正余额仍计入估算总量。 |
| 百分比超范围、非有限数或字段互相矛盾 | 未知并报告归一化异常，不能静默修成正常额度。 |
| 快照不足一分钟，但 `status=error` | 旧数据可灰显，不能参与推荐。 |
| 认证失效账号与可靠可用账号并存 | 推荐可靠账号，提示覆盖不完整。 |
| `origin=cockpit_cache` 且缓存看起来很新 | 不参与 `now` 或确定等待时间推荐。 |
| 默认 5 分钟刷新，快照年龄恰好 10 分钟 | `stale`，排除推荐。 |
| 改成每 1 分钟刷新，快照年龄恰好 2 分钟 | `stale`。 |
| 改成每 30 分钟刷新，快照年龄 59 分钟且无重置边界 | 可保持 fresh；年龄达到 60 分钟则 stale。 |
| 新鲜快照中适用基础窗口 `resetsAt=T` | `unknown / awaiting_confirmation`，只触发合并刷新。 |
| 倒计时已结束，但网络不可用 | 不恢复为 `now`，展示等待更新或错误原因。 |
| 重新请求仍返回已过去的 reset | 继续未知，执行退避，不能反复即时刷新。 |
| 一账号 `now`，其余账号均 `waiting` | 推荐 `now` 账号。 |
| 多账号均 `now`，周窗口分别于 `T+1d`、`T+2d` 重置 | 推荐 `T+1d` 账号。 |
| 一账号有已知周 reset，另一账号没有适用周窗口，两者均可用 | 已知周 reset 账号优先；另一账号仍是有效候选。 |
| `secondary` 时长为 86,400 秒 | 不作为 7d 排序依据，展示真实时长。 |
| 所有账号均 `waiting`，各自最终恢复时刻为 `T+3h` 和 `T+2h` | 推荐 `T+2h` 账号。 |
| 一账号 `waiting`、一账号 `unknown` | 可显示已知账号的预计恢复，但明确覆盖不完整。 |
| 多账号排序时间相同且显示名相同 | 先按用户顺序、再按 ID，结果稳定。 |
| 未选择账号 | 展示选择账号空状态，不发送配额请求。 |
| 请求未完成时账号被取消选择，旧响应随后成功 | 丢弃旧响应，不重现账号、不改变推荐。 |
| 刷新中的历史快照仍新鲜且有效 | 可以保留旧推荐和旧成功时间，不能宣称已刷新。 |
| 失败后再次进入 refreshing，旧成功值仍很新但 error 未清除 | 保持 unknown，成功查询前不能重新参与推荐。 |
| 刷新期间历史快照超龄或跨越 reset | 立即变为 unknown，不等请求完成。 |
| 系统睡眠跨越多个定时刷新周期 | 唤醒后合并刷新，不补发全部错过的请求。 |
| 系统时间回拨导致成功时间位于未来 | 不利用负年龄延长有效期；校验后重新查询。 |

这些用例应首先用于领域纯函数、时间推进和刷新竞争的测试。配额响应字段的适配测试另外使用按上游版本固定的脱敏 fixture，避免把外部接口的偶然行为写成领域事实。

## 0.1.3 推荐门槛修订（优先于早期 > 0 规则）

5h 剩余 < 5% 或周剩余 < 2% 时不参与当前可用推荐，原始额度和 exhausted 标记保持服务端语义。已知相关窗口重置时间时状态为 waiting，未真正耗尽的原因是 below_threshold；多个窗口不足取最晚重置时间，缺失则 unknown。恰好 5% / 2% 允许推荐。重置时间到达仍需查询确认，不能本地恢复额度。通过门槛后沿用最早周重置优先的排序。
